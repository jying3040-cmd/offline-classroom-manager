## 整理原则

1. **单一来源**：源码保留在 ASCII 路径以兼容 Flutter Windows 构建。仓库文档为权威来源，工作区与交付文档入口通过 junction 访问，不保存独立副本。
2. **按用途与版本划分**：当前版与历史版分开，说明跟随版本。旧运行目录归档保留，不混合不同版本的 DLL、AOT 与资源。
3. **以内容确认去重**：SHA-256 相同才判定文件重复。体积、名称相似不构成删除依据。zip 与解压目录分别服务分发和直接运行，均保留。
4. **保留必要资源**：离线音频、字体、运行时 DLL、数据库迁移、被复用的 audio_import 和 Repo.importWords、已下线页面归档均保留。当前机器缺少 Visual Studio，build 中既有原生 runner 供 AOT 重建复用，不能一律删除构建目录。
5. **临时数据与真实数据区分**：`classroom_v4_test_*` 是被 Git 忽略的临时测试目录，可以清理；不访问或清理真实 `%APPDATA%` 教师数据，不因文件整理启动数据库迁移。
6. **Git 管理可维护输入**：源码、资源、脚本和文档提交到仓库；发布 zip、exe 和本机 junction 留在交付工作区。整理后正常推送，不改写历史、不强推。

## 后续维护

构建后先备份已有运行目录，在交付根目录建立版本目录；验证资源完整后生成 zip，再解压启动验收。升级完成将上一版本移入历史目录，更新本文与交付路径。旧版回退可能涉及数据库兼容性，应先备份教师数据。

文件完整性可在源码根目录运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/verify_delivery.ps1
```

脚本只读校验交付文件，不启动应用或写教师数据。当前固定校验 4.0 与 1.0–3.0 历史包，升级时同步调整清单。
